# Working on this plugin with Claude

Context for Claude Code and any other coding agent working in this repository.
It is also the shortest accurate description of the plugin model here, so it is
worth reading yourself.

## What this repository is

A **SoundBase plugin** for the Shure ADTQ, a four-channel Axient Digital PSM
in-ear-monitor transmitter: a small network service that provides the unit to
SoundBase over a versioned HTTP + SSE contract. SoundBase spawns it as a child
process and supervises it — handshake, health, crash-restart, teardown. The
plugin in turn holds one ACN (ANSI E1.17) session per unit, the protocol
Wireless Workbench uses, and pushes the unit's state to SoundBase as it
changes.

SoundBase is an RF coordination platform for live events. This plugin lands in
its **device monitoring** views: a card per channel showing what the
transmitter is doing, with RF mute, frequency, RF power and audio mode
controllable from it. `docs/soundbase.md` is the orientation.

The author writes device logic. The author never writes UI, IPC, or HTTP.

```
soundbase-plugin.json   identity, the product, its layout, config fields, state keys
main.js                 shell bootstrap — never edit
adapter.js              the device on the contract — the file that changes
driver/
  acn/crypto.js         session key (skUtil), AES-CTR at a stream position, SKIP32 tag
  acn/pdu.js            ACN root/SDT/DMP codec; JOIN, wrappers, client blocks, DmpDecoder
  acn/slp.js            SLP request + controller advert + reply parser; SlpBrowser
  acn/session.js        AcnSession: the prologue, acks, NAK retransmit, request/reply
  adtq/properties.js    the address map, evidence grades, value codecs
  adtq/device.js        AdtqDevice: discover, connect, typed reads/writes with read-back
  fake/fake-adtq.js     FakeAdtq: the same wire, no hardware; also the in-app simulator
__tests__/              vectors from the Python reference, driver vs fake, adapter via shell
scripts/adtq.mjs        the command-line tool for a real unit
docs/adtq-protocol.md   the wire, in full
docs/adtq-properties.md the property map and the evidence behind each address
```

## Invariants — do not violate these without being asked

- **Never edit `main.js`.** It is byte-identical across every first-party
  plugin. Anything you are tempted to put there belongs in `adapter.js`.
- **Never implement HTTP, routing, SSE, auth, or state-patch bookkeeping.**
  `@soundbase/plugin-shell` owns all of it.
- **Every write reads back.** `AdtqDevice`'s setters SET, then GET the same
  address, and report `ok` only when the device holds what was written. The
  adapter reports the read-back as state, whether or not it matches the
  request. A SET the device ignores is otherwise invisible; do not add a
  write path that skips the read-back. A SET_FAIL is a definite answer: it
  is surfaced as `refused` with the reason, and the read-back that follows
  it is still collected.
- **The device CID is mandatory and comes from SLP.** A JOIN addressed to a
  CID the device does not own is dropped with no reply of any kind. Never
  fall back to a guessed or hardcoded CID; fail with a message that says
  UDP/8427.
- **Keep the protocol constants byte-exact.** `__tests__/fixtures/acn-vectors.json`
  was generated by the Python reference (`ADTQ Mute/engine`) and pins the
  session key, keystream, tag, every PDU builder and the SLP advert. A change
  that fails those tests is a change to the wire, and the wire is the device's.
- **Reliable-sequence lockstep.** JOIN advertises the reliable base as our
  channel number; the first reliable wrapper must be chan+1. The reciprocal
  ASSOC0a must carry the *device's* channel. The first DMP waits out the
  write gate. Each of these, wrong, produces total silence with no error.
- **Silence means a lost packet, never an absent property.** The device
  answers every GET with a reply or a GET_FAIL. Reads retry; a fully silent
  refresh is probed once more and then reported through `onFatal`.
- **Gain and encryption stay read-only.** Deliberate: gain is level in
  someone's ears, encryption forces every receiver to re-sync. Show, do not
  set.
- **RF power is an extension key, not `txPower`.** The device's enum has no
  honest milliwatt mapping. Do not invent one.
- **Nothing unconfirmed on the card.** `docs/adtq-properties.md` grades every
  address; only *confirmed* ones are exposed. To add one, identify it with
  `watch` and a stated prediction first, then add it to `CHANNEL_PROPS`.
- **Device ids are stable:** `net:<ip>` for real units, `sim:adtq` for the
  simulator. They are stored in users' projects.
- **Do not bump the `template` block** in `soundbase-plugin.json`.
- **The layout lists nodes in card order.** SoundBase places channel nodes by
  type: meters, then the first four `value`/`indicator` nodes as cells, the
  `mute` indicator as the large cell. `group` and `direction` do not arrange
  them. Put what belongs on the card first; mark the rest `"region": "detail"`.
- **The mono label is keyed by the driver's string.** Both meters carry
  `labelFrom: { bind: "audioModes.txMode", map: { "mono": "M" } }`; `mono` is
  the value `AUDIO_MODES` reports, and a test holds the two together.
- **The declared ChannelMonitoring version is the installed SDK's.** The
  layout uses 1.1 properties (`meterStyle`, `region`, `labelFrom`), and the
  shell reports it to SoundBase through the installed contract package: one
  that implements less drops them silently. Never lower the SDK below 0.12.2,
  and move `contract.modules.ChannelMonitoring` in the same change as any SDK
  bump that changes `CM_MODULE_VERSION`. A test holds the two together.

## The adapter contract

```js
export async function discoverDevices(pluginConfig) → Device[]   // the SLP browse table, at once
export function createMonitoringAdapter(device, pluginConfig) → {
  open()                 → { channelCount: 4, properties, identity }; reports full state first
  close()
  setProperty(command)   → write, read back, report the read-back through onState
  onState, onWarnings, onFatal   assigned by the shell
}
```

The normative specification ships with the SDK:

```
node_modules/@soundbase/plugin-contract/spec/
  soundbase-plugin.schema.json  core.openapi.yaml
  channel-monitoring.openapi.yaml  property-control.openapi.yaml  state-keys.json
```

**Read those before answering a question about the contract.**

## Verifying a change

```sh
npm run doctor    # is the plugin well-formed at all?
npm test          # vectors; driver against the fake; adapter through the shell
npm run manifest  # the manifest the host will refuse or accept
npm run smoke     # boots as a child process, handshakes, drives the simulated unit
npm run adtq -- status <ip>    # the real thing, when a unit is in reach
```

Against a real ADTQ ("ADTQ G57 NACLOCK", 2026-09-08) this port has run
`discover` and `status`: SLP found the unit with its CID, the session
associated, and every mapped property of all four channels read back decoded.
One kind of write has been made from this port: channel names, which found
that the name's read address is not writable and `0x0001` is. On 2026-09-09
the audio level addresses were identified with programme on CH1 (a mono flip
and a right-only feed, both predicted in advance) and pair B went on the card
as the L/R meters, polled every 100 ms by default, with the panel's 7-dot meter byte
(`0x01d5`/`0x01d6`, a bitmask with a peak-hold dot, decoded against the panel
through a gain sweep) alongside as `x.shure-adtq.afDots`. RF mute has not been written from this
port; the Python tool it was ported from has muted the unit. The next step
with hardware is a single `mute … on`/`off` on one channel, before anything
in SoundBase.

## Prompts that work

**Exposing another property**

> Identify it first: `npm run adtq -- watch <ip>` while changing the control
> in Workbench on one channel, and state the expected address and value
> before the second data point. Then add it to `CHANNEL_PROPS` in
> `driver/adtq/properties.js` with its decoder, give the fake a plausible
> value in `defaultProperties()`, map it to a state key in `emitAll()` (a core
> key from state-keys.json if one fits, else `x.shure-adtq.<key>` declared in
> the manifest's `stateKeys`), bind it in the layout, and extend the
> through-the-shell test.

**Making a property writable**

> Add a setter on `AdtqDevice` that SETs and reads back, a `case` in
> `setProperty` with boundary validation that throws `HttpError(400, …)`, a
> descriptor in `propertyDescriptors()`, and a `control` node if it belongs
> on the card. The fake's `applySet` decides what the fake accepts; keep it
> honest about what the real unit is known to do.

**Diagnosing "the unit is found but nothing changes"**

> Work outwards with the CLI: `discover` (does SLP answer, with a CID?),
> `status` (does the session associate and read?), `mute` (does the write
> land — CONFIRMED or NOT APPLIED?). NOT APPLIED with a live session usually
> means Workbench is also holding one. No association at all means the CID,
> the port, or a firewall on UDP/8427. `docs/adtq-protocol.md` lists the
> silent failure modes.

## What not to ask for

- **A second transport.** The contract is HTTP plus SSE; the device is ACN.
- **UI.** The layout in the manifest is the card; SoundBase renders it.
- **Changes to the shell.** Raise an issue instead of a workaround.
- **Meters that claim more than is confirmed.** The readings at
  `0x0117`-`0x011a` and `0x01d3`-`0x01d6` are post-gain audio levels in
  left/right pairs with the sides confirmed (`docs/adtq-properties.md`,
  "Audio levels"). What distinguishes the three dB pairs is not, and the dB
  reference is unverified. A meter labelled with a scale or a meaning nobody
  has demonstrated is worse than none.
- **Talking to a unit Workbench is controlling.** One controller at a time.
